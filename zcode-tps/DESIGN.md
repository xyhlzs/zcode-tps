# ZCode TPS 监控 · 设计文档 v2

面向两条实测反馈：**刷新率偏慢**、**多任务并发时不清楚显示的 TPS 属于哪个任务**。

本文档只写结论和依据，不写实现细节。所有「实测」都标注了测量方式；没有标注的
是推断或待验证。

---

## 1. 背景

现状实现（v1）是一个 ZCode 插件：`SessionStart` hook 拉起常驻的 PowerShell 守护
进程，它 tail `~/.zcode/cli/rollout/model-io-<sessionId>.jsonl`，按
`outputTokens ÷ durationMs` 算速率，画在置顶小窗上。会话归属靠 tail 日志里的
激活事件（`turn.started` 等）加 30s 新鲜度、再回落到最新写入的文件。

v1 能工作，但有两个结构性缺陷，就是这次的反馈。

---

## 2. 需求分析

### R1「刷新率有点慢」

先把反馈拆开，因为这**不是定时器问题**——当前定时器是 400ms，已经足够快。
问题在于 400ms 到点时**数据源根本没有新数据**。

**实测**：取一次 26.2 秒的生成，统计该请求起止时间窗内日志文件里的全部事件，
只有 19 条，且全是首尾成对的（`model.request.started/completed`、
`model.sdk.stream.completed` 各一条），中间**没有任何逐块事件**。
另一次 38.4 秒的窗口里，最频繁的 `session.event.persistence.*` 间隔中位数是
3.39 秒。

**结论**：从外部看，一次生成过程中不存在亚秒级的进度信号。速率数字只能在
「一次模型请求结束」时更新，而一次请求可持续 30–60 秒，所以数字长时间不动。

拆成可验收的子需求：

| 编号 | 需求 | 验收 |
|---|---|---|
| R1-1 | 生成过程中，界面要能明确表达「正在生成」并且有东西在动 | 空闲/生成中可区分，生成中计时器 ≤1s 刷新 |
| R1-2 | 速率数字的更新间隔要短于「一次请求」 | 同一请求内至少能多更新 1 次 |
| R1-3 | 数字必须有依据，不能是编的 | 每个数字都能溯源到某一层信号 |

### R2「并发多任务时不知道是哪个窗口的」

**先纠正一个前提**：实测枚举所有可见顶层窗口，ZCode **只有一个窗口**，
窗口标题固定是 `ZCode`，不带会话名。用户说的「哪个窗口」实际指「哪个任务」。

**同时，并发是常态而非例外**：对数据库每 0.5 秒采样一次、共 258 次采样，
其中 **247 次**同时有 2 个会话在近期有内容更新。

所以 v1 的「猜一个会话并只显示它」这个思路本身就不成立——并发时无论猜哪个，
都会让用户看着数字犯嘀咕。拆成：

| 编号 | 需求 | 验收 |
|---|---|---|
| R2-1 | 显示的任务标识要人能读懂 | 显示任务标题，而不是 id 前 8 位 |
| R2-2 | 并发时不能只给一个数字 | 所有并发活跃任务都能看到各自的速率 |
| R2-3 | 归属要可核对 | 每一行都能对应到侧边栏里能认出来的任务 |

### 非目标

- 不做子代理（`sess_subagent_*`）的独立展示，它们在父会话内被计数即可。
- 不做历史报表、导出、聚合统计。
- 不试图复刻 ZCode 自身的界面。

## 3. 信号盘点（实测）

这是本文档最重要的部分：**决定设计的是数据源到底给什么**。

| 数据源 | 内容 | 时间粒度 | 成本 | 实测依据 |
|---|---|---|---|---|
| `rollout/model-io-*.jsonl` | 真 token 数（`usage.outputTokens`）、`durationMs`、`turnId`、`sessionId` | **一次请求结束** | 读尾部 8MB，秒级 | v1 已用 |
| `log/zcode-*.jsonl` | 生命周期事件、`model.request.started` / `.completed`（同 spanId） | 事件即时 | 极小 | 生成期间无逐块事件 |
| `db.sqlite` → `part` | **流式内容本身**（`type: reasoning/text/tool` 的 JSON）、`session_id`、`time_updated`、`sequence` | **中位 3.5s 一次、跳跃式**（见 3.1） | 索引查询 0.17ms | 118532 行 |
| `db.sqlite` → `session` | **会话标题** `title`、`time_updated` | 随会话活动 | 0.2ms | 218 行 |
| ZCode 窗口 | 窗口标题 | — | — | 只有一个窗口，标题固定 `ZCode`，**无法用于归属** |

### 3.1 `part` 的落库粒度（关键实测）

对 `part` 表每 0.08 秒采样一次（实测 4.4 Hz），累计 **641 个样本 / 147 秒**，
跟踪每个 part 的 `length(data)`：

```
观察到的 part 总数             87
长度始终未再变化               68   (78%)
变化 1 次                     13
变化 2 次                      6
─────────────────────────────────────
长度变化事件总数               25    ≈ 10 次/分钟
相邻两次变化的间隔中位数         3.46 s
与前一次变化相距 ≤0.5s 的比例    25%
```

也观察到过 part 在**未完成时就被写进库**（775 → 1799 字节），以及 3 个 part 的
尺寸变化落在同一时刻（12.69s）的成簇现象——但成簇只占 25%，不是常态。

**结论**：DB 的更新间隔**中位数约 3.5 秒**，比「一次请求」（30–60 秒）快约一个
数量级，但**不是平滑流**：字节以跳跃方式补齐，一个 part 通常只补 1–2 次。
它能支撑「每几秒动一次」的估算，撑不起逐字跳动的曲线。

### 3.2 查询代价（决定架构）

- `where time_updated > ? order by time_updated desc`（v1 探针用的写法）：
  `part.time_updated` **没有索引**，全表扫 118532 行，**平均 241ms**。
  按 400ms 周期轮询等于常年占用一个核。
- 改走已有复合索引 `(session_id)` / `(message_id, sequence)`：
  「最新 message」0.07ms，「该 message 的 parts」0.02ms，
  「3 个会话的标题 + 各自最新消息字节数」整体 **0.17ms**。

即：**轮询必须由已知的 session_id 驱动，绝不能按时间扫 `part`**。差三个数量级。

### 3.3 SQLite 访问路径

PowerShell 5.1 没有 SQLite provider（.NET Framework 不带 `Microsoft.Data.Sqlite`，
也没有系统级 ODBC 驱动）。已验证本机 **node v24.21.0 内置 `node:sqlite`**，可只读
打开该库并成功读出 `session.title`。这构成一条无需打包原生 DLL 的访问路径，
代价是引入 Node 运行时依赖。

## 4. 设计目标

1. 生成过程中界面**有东西在动**，且明确区分「生成中」与「空闲」（R1-1）。
2. 速率数字的更新频率高于「一次请求」，且**在飞行的速率标注为估算**
   （R1-2、R1-3）。
3. 并发时**并列展示所有活跃任务**，各自带可读标题（R2-1、R2-2、R2-3）。
4. 没有 Node 时**优雅降级**回 v1 行为，不崩。
5. 稳态 CPU 占用 < 1% 单核。

---

## 5. 总体架构

```
                 ┌──────────────────────────────┐
                 │  PowerShell 主进程（渲染 + 编排）│
                 │  · 置顶小窗（DPI 感知、置顶断言）│
                 │  · tail rollout（真 token 数）  │
                 │  · tail log（在飞状态、激活事件）│
                 └───────┬──────────────┬────────┘
                         │ 读快照 JSON   │ tail
                 ┌───────▼──────┐  ┌────▼─────────────┐
                 │ node sidecar │  │ rollout / log     │
                 │ 轮询 db，4Hz  │  │ （ZCode 写的）     │
                 └───────┬──────┘  └──────────────────┘
                         │ 索引查询 0.17ms
                 ┌───────▼──────┐
                 │  db.sqlite   │
                 └──────────────┘
```

sidecar 是一个**长驻**的 node 进程（不是每次轮询起一个——node 冷启动约 50–100ms，
按 4Hz 起进程会立刻把收益吃光）。它每 250ms 用带索引的查询取一份小快照，
写到约定的交换文件（或标准输出被主进程读取）。主进程只管渲染，不直接碰 sqlite。

**为什么不让主进程直接读库**：PowerShell 读不了；且把 SQL 与轮询节奏集中在一个
能便宜访问库的进程里，主进程保持「只读文本文件」的简单模型。

## 6. R1 设计：让刷新率真的提上去

分三层信号，**每层的诚实度不同，UI 上要能看出来**。

### L1 在飞状态（真值，即时）

tail 日志的 `model.request.started` 与 `model.request.completed`（按 `spanId` 配对）。
有 started 无 completed = 该会话正在生成。据此渲染：

```
生成中 · 已 12.4s
```

计时器按刷新周期（250ms）走。**这一层是纯真值**，也是解决「数字不动看着像卡死」
的主要手段——用户能确认系统在工作。

### L2 请求完成时的精确速率（真值，权威）

沿用 v1：请求结束、rollout 落盘后，用 `outputTokens ÷ durationMs` 覆盖显示。
同时在请求结束时用真值**修正 L3 的换算系数**。

### L3 在飞期间的估算速率（估算，必须标注）

数据来自 sidecar：跟踪该会话**当前 message** 的 `Σ length(part.data)` 变化。

- 字节增量 ΔB / Δt → 字节速率；
- 乘以换算系数 k（token/字节）得到 token 速率估计；
- k 由最近若干次已完成的请求标定：`k = Σ outputTokens ÷ Σ 对应 message 的最终字节数`。

因为 3.1 已实测落库是**中位 3.5 秒一次的跳跃式补齐**，L3 必须：

- 用 **5 秒滑动窗口**计算，而不是取相邻两次采样的差；
- 窗口内刷入次数 < 2 时不显示速率，只显示 L1 的「生成中 · 已 Xs」；
- 显示为 `≈ 62 tok/s`，与 L2 的真值样式区分（L2 无 `≈`）。

预期效果：一次 40 秒的请求里，L3 能把数字更新 5–10 次（v1 是 0 次），
L1 的计时器则每 250ms 都在动。

若实测发现 k 的波动过大（见验收 A4），L3 降级为**只显示字节速率**或直接去掉，
不影响 L1/L2。

## 7. R2 设计：归属

### 7.1 标题

sidecar 从 `session` 表读 `title`（0.2ms）。取不到时回退到 v1 的 `id` 前 8 位。

> **已全部落地（0.3.0）**：sidecar 按 §8 契约输出 titles + sessions（活跃集合、
> 当前 assistant message 的分类型字节计数），经交换文件递给主进程。标题显示于
> 单会话卡片元信息首行右列；多行并列（§7.2）与 L3 估算（§6）均已实现并有回归测试
> （tests/estim-test.ps1、tests/sidecar-test.mjs）。实测注意：part 计数口径是
> UTF-16 码元（与 SQLite `length(text)` 的字符数同基准），k 的标定与使用同口径自洽；
> 标定只认 30s 内完成的请求，基线仅在配对成功后消费——启动回看的历史记录
> 会以 dR=0 误消费基线，是测试抓出来的实现坑。

### 7.2 多会话并列

把「猜一个」改成「全都列出来」。活跃会话集合 = `session.time_updated` 在最近
窗口内（初值 5 分钟）的会话，**排除** `task_type = 'subagent_child'`。

界面随活跃数量自适应：

```
┌────────────────────────────────────────┐
│ ZCode TPS                      ×       │
│  1  一次性重命名所有文件   ≈62  tok/s  │ ← 在飞：高亮 + 计时
│     已 12.4s                           │
│  2  MSPL λ=0.5 模块实验    48.1 tok/s  │
│  3  软著合作开发协议        —          │
└────────────────────────────────────────┘
```

- 每行：**序号 + 标题（截断）+ 速率 + 状态**；
- 在飞行置顶并高亮，空闲行按 `time_updated` 降序；
- 行数上限 5，超出折叠为 `+N`；
- 单会话时退化为 v1 的紧凑卡片（不浪费屏幕）。

这直接满足 R2-2/R2-3：并发不再是一个需要猜的问题，而是**并列展示**；
标题与侧边栏一致，用户能自己核对。

### 7.3 与 rollout 的对齐

多行展示需要每个会话各自的速率，而 rollout 是真值的唯一来源。做法：**对每一行
各自 tail 对应的 rollout 文件**（同一套解析代码，按会话维护独立游标与统计）。
rollout 目录里只有主会话文件，子代理不计（已实测）。

## 8. 数据契约

sidecar 每 250ms 覆盖写一次交换文件（写临时文件 + `File::Copy` 覆盖，
理由见 v1 踩过的 `Move-Item` 权限坑）：

```json
{
  "t": 1790577494571,
  "sessions": [
    {
      "id": "sess_918494db-...",
      "title": "一次性重命名所有文件",
      "lastActiveMs": 1790577490000,
      "msgSeq": 127,
      "bytes": 9457,
      "parts": [ {"seq":1,"type":"reasoning","bytes":7329,"updatedAt":1790577490000} ]
    }
  ]
}
```

字段约束：

- `title` 由 SQL 侧截断到 60 字符，避免超长标题撑爆交换文件；
- `parts` 只保留**当前 message** 的（其上一条 message 的字节数没有实时意义）；
- 整体大小上限约 4KB，4Hz 写入的 IO 可忽略。

## 9. 降级与容错

| 故障 | 行为 |
|---|---|
| 没有 node / `node:sqlite` 不可用 | 跳过 sidecar，退回 v1：单会话 + `id` 前 8 位 + 无 L3；UI 底部标注「精简模式」 |
| sidecar 进程死了 | 主进程按 `t` 时间戳检测陈旧，重启 sidecar；连续失败 3 次后进入精简模式 |
| db 被 ZCode 独占 / 打开失败 | 本次轮询跳过，不影响 L1/L2 |
| 交换文件读到半截 | 契约要求原子覆盖；主进程解析失败则沿用上一份快照 |
| `part` / `session` 表结构变更 | sidecar SQL 报错 → 记录到日志 → 主进程仍显示 L1/L2 |

**sidecar 绝不能拖垮主进程**：主进程不等待 sidecar，读到什么用什么。

## 10. 验收标准

| 编号 | 标准 | 测量方式 |
|---|---|---|
| A1 | 生成中，界面每 ≤1s 有一次可见变化 | 录屏逐帧核对 |
| A2 | 空闲与生成中在 1 秒内可区分 | 同一手段 |
| A3 | 两个会话同时生成时，两行都出现且标题与侧边栏一致 | 受控并发测试 |
| A4 | L3 估算速率与 L2 真值的偏差 ≤ 20% | 每个请求完成时对比，统计 20 次 |
| A5 | 稳态 CPU < 1% 单核 | 任务管理器 / `Get-Process` 采样 |
| A6 | 无 node 环境不报错、功能降级 | 临时改名 node 可执行文件后启动 |
| A7 | 单次刷新（含 sidecar）< 50ms | 主进程计时埋点 |

A4 是 L3 是否保留的**放行门槛**。

## 11. 验证方案

1. **受控并发（A3）**：同一窗口开两个任务，各发一条长指令，检查两行同时出现、
   标题正确、在飞状态各自独立。
2. **换算系数标定（A4）**：脚本化的采样 —— 每个 `model.request.completed` 触发时，
   记录 rollout 真 token 数与当时 L3 的估算值，做配对统计。
3. **落库粒度复测**：若后续 ZCode 版本改变落库策略（比如变成逐块），L3 的可用性
   会显著提升，需要用同一套 0.08s 采样脚本复测，作为重新评估的依据。
4. **降级路径（A6）**：见 v1 的合成日志手法，构造无 node / 坏快照两种输入。
5. **回归**：v1 的会话跟随三阶段单测（合成日志：日志指 A → 目标 A；日志改指 B →
   覆盖 mtime；B 闲置 120s → 回落 mtime）必须继续通过。

## 12. 风险与开放问题

| 风险 | 影响 | 处置 |
|---|---|---|
| 落库是中位 3.5s 一次的跳跃，不成流 | L3 数字会一跳一跳，不是平滑爬升 | 5 秒滑动窗口 + `≈` 样式如实标注；A4 不过就砍掉 L3，只留 L1/L2 |
| 引入 Node 依赖 | 不再是零依赖 | 保留精简模式；README 写明 |
| `part.data` 是 JSON 文本，字节数≠token | k 波动可能很大（工具调用 JSON 与自然语言的比例不同） | k 按 part 类型分别标定（`reasoning` / `text` 不含 `tool`） |
| 内部表结构随版本变更 | sidecar 失效 | SQL 集中在 sidecar 一处，便于修 |
| 700MB 库 + WAL 并发读 | 与 ZCode 争 IO | 只读连接、带索引、4Hz，实测 0.17ms/次，风险低 |
| 5 分钟活跃窗口可能列出太多会话 | 界面拥挤 | 行数上限 5 + 折叠 |

**开放问题**：能否用 UI Automation 读渲染区里正在流式的文本长度，从而拿到真正的
逐字速率？这条路不依赖落库粒度，但依赖 Chromium 的无障碍树，实现与稳定性都未验证。
建议作为独立 spike 排在 L3 之后，**不作为本次设计的组成部分**。

---

## 13. 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 用日志事件密度当速率代理 | 实测：生成期间日志几乎无事件（26.2s 窗口内仅 19 条，全是首尾成对），密度与 token 速率无关 |
| 用 ZCode 窗口标题做归属 | 实测：只有一个窗口且标题固定为 `ZCode`，无信息量 |
| 用焦点窗口决定显示哪个会话 | 同上，无法区分任务 |
| 打包 `System.Data.SQLite.dll` 给 PowerShell 用 | 需同时带原生 `SQLite.Interop.dll`，体积与位数匹配成本高于 `node:sqlite` |
| 提高定时器频率来解决「慢」 | 定时器已 400ms；瓶颈是数据源，提频只会空转 |
| 继续「猜一个会话」并加强跟随 | 并发是常态（247/258），猜错时用户无法察觉，问题不在猜测精度 |

## 14. 落地拆解

1. **sidecar**：node 脚本 + 带索引的 SQL + 原子写交换文件；独立可跑，可单测。
2. **主进程读快照**：解析、陈旧检测、重启 sidecar、精简模式开关。
3. **多行 UI**：行布局、标题截断、在飞高亮与计时、折叠。
4. **每会话 rollout tail**：把 v1 的单游标改成按会话的游标表。
5. **L3 标定与显示**：k 按 part 类型标定、滑动窗口、`≈` 样式、A4 门槛判定。
6. **降级与容错**：把第 9 节的表逐条实现并测试。
7. **回归**：v1 跟随三阶段单测 + A1–A7。

每步独立提交，保持 v1 功能可用（可回退）。
